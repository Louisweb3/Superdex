---
name: Multi-chain 0x swap support (Base + Robinhood Chain)
description: How SuperSwap added a second EVM chain (Robinhood Chain) to the existing Base-only 0x-powered swap without breaking the fee model, and how its real token/liquidity data is sourced.
---

The swap backend and frontend hooks were hardcoded to a single chainId. To support a second chain sharing the same 0x router and fee wallet:

- Server: replace the hardcoded chainId constant with a small allow-list (`SUPPORTED_CHAIN_IDS`) and a `resolveChainId()` helper that defaults to the primary chain if the client passes an invalid/missing value. Both `/api/swap/price` and `/api/swap/quote` read `chainId` from query params. The fee recipient wallet is untouched — 0x lets the same fee wallet receive fees on any chain it's deployed on.
- Client hooks (`useSwapPrice`, `fetchSwapQuote`) take an explicit `chainId` argument threaded from the page state, not inferred from `window.ethereum` — this keeps quotes correct even before the wallet has switched networks.
- Network selection state should sync FROM the wallet's connected chain (via effect) but also be independently settable by the user (toggle UI) so users can browse quotes for a chain before switching their wallet to it.
- Pitfall: any "default buy token" fallback logic that hardcodes a Base-only address (e.g. Base USDC) must be branched per-network — falling through to a Base token object when the other chain's list is momentarily short silently selects a token that doesn't exist on that chain, breaking quotes with no obvious error.

**Robinhood Chain (chainId 4663) DOES have real DEX liquidity** — 0x's `liquidityAvailable` and Uniswap V3/V4 fills are real when queried with actual Robinhood Chain token addresses (confirmed via `/api/swap/price`). An earlier investigation wrongly concluded the chain had no liquidity because it tested with a *Base*-chain token address (e.g. Base's USDC contract) while passing `chainId=4663` — that pair trivially has no liquidity since the token doesn't exist on that chain at all. Always test chain-specific liquidity using addresses that actually exist on that chain, not addresses copied from another chain's token list.

**Robinhood Chain token discovery**: its own Blockscout explorer instance (`https://robinhoodchain.blockscout.com/api/v2/tokens?type=ERC-20`) indexes every deployed ERC-20, with open CORS, returning symbol/name/decimals/icon_url/exchange_rate/holders_count (includes stablecoins USDC/USDG/USDE, WETH, and Robinhood's tokenized-stock assets like AAPL/TSLA/NVDA). Correction: DexScreener *does* also index this chain under `chainId: "robinhood"` (`https://api.dexscreener.com/tokens/v1/robinhood/{addr1,addr2,...}` bulk endpoint, up to ~30 addrs/call) — but its coverage is partial (e.g. USDE has zero DexScreener pairs despite having real, confirmed 0x-routable liquidity). Lesson: use Blockscout as the source-of-truth token list (never drop a token just because DexScreener lacks a pair for it) and use DexScreener only to enrich icon/price/trending-flag data when available — a missing DexScreener pair is not proof of no liquidity, only an actual 0x price/quote call is. `client/src/hooks/useRhTokens.ts` implements this Blockscout-primary + DexScreener-enrichment pattern.

**Robinhood Chain's tokenized stocks are NOT tradeable via 0x**: Robinhood deployed real ERC-20s for stocks/ETFs (NVDA, TSLA, AAPL, SPY, QQQ, etc.) but 0x's own compliance layer rejects any quote involving them with `BUY_TOKEN_NOT_AUTHORIZED_FOR_TRADE` / `SELL_TOKEN_NOT_AUTHORIZED_FOR_TRADE` ("legal restrictions") — this is permanent and not a bug to fix. Blockscout's `name` field reliably tags these with a `"• Robinhood Token"` suffix (e.g. `"Tesla • Robinhood Token"`), so filter them out of the swap token list entirely rather than letting users pick a token that will always 422. If a 0x error response has `name` matching either of those two strings, surface a clear "restricted from trading" message instead of a generic liquidity error.

**Multi-chain network-toggle chain-mismatch bug**: when a swap UI has both a wallet-driven chain and a manual in-app network toggle (e.g. a "Base / Robinhood" button pair), a wallet-level `isWrongNetwork` flag that only checks "is this chain ANY of our supported chains" is not sufficient — it will be `false` even when the wallet's actual connected chain doesn't match the currently-selected UI network. This lets the swap button stay enabled and send a transaction built for chain A's contracts while the wallet is still on chain B, which silently fails (contract doesn't exist there) and looks exactly like "no liquidity" or "swap doesn't work" to the user, even though price/quote calls (read-only, chain-id passed explicitly) succeed fine. Always compute a *second*, UI-selection-aware mismatch check (`wallet.chainId !== currentlySelectedNetworkChainId`) and gate both the swap button AND the actual send-transaction call on it — a stale toggle should force "Switch Network," not "Swap Now."

**Why:** keeps the two chains' data sources cleanly separated (Base token list must never leak into the other chain's picker) while reusing 100% of the swap execution path (0x router, approve/allowance flow, fee wallet).

**How to apply:** when adding a further chain, extend `SUPPORTED_CHAIN_IDS` server-side, add a Blockscout-or-equivalent-backed token hook client-side, add a case to the network toggle, and verify liquidity by testing with real addresses from that chain's own token list — never assume "no indexed database" means "no liquidity."
